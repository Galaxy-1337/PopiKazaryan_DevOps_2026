# Правила внесения и приёмки изменений

Документ фиксирует обязательный порядок работы с репозиторием проекта «Конференция».
Требования одинаковы для всех: для участников команды, для преподавателя и для изменений,
созданных средствами автоматической генерации кода.

> Любое изменение рассматривается как потенциально ошибочное. До попадания в `main` и до
> выпуска оно проходит автоматические и организационные проверки.

---

## 1. Путь изменения

```
задача → ветка → изменение кода → make verify → коммит → push → Pull Request → CI → review → merge в main → тег
```

Ни один шаг нельзя пропустить. Прямой push в `main` запрещён настройками репозитория.

## 2. Обязательные команды локальной проверки

Перед каждым коммитом и перед созданием запроса на слияние выполняется:

```bash
make verify
```

Команда выполняет полный набор проверок:

| Шаг | Команда внутри | Что проверяет |
|---|---|---|
| 1 | `ruff format --check .` | единый формат кода |
| 2 | `ruff check .` | статический анализ, ошибки и потенциальные дефекты |
| 3 | `pytest -q` | 55 автоматических тестов, включая все правила предметной области |
| 4 | `python -m scripts.smoke` | приложение действительно поднимается и отвечает на ключевые адреса |

Под Windows без GNU make используется полный аналог:

```powershell
.\scripts\dev.ps1 verify
```

Дополнительно, если менялась работа с базой данных:

```bash
make migrate                     # схема создаётся без ошибок
make backup                      # резервная копия делается
```

Если менялась работа с контейнерами:

```bash
make up
make container-check             # /health внутри контейнера отвечает
make down
```

Правило: **локально должно быть зелёно до отправки изменений**. Если проверка падает,
исправляется код, а не проверка.

## 3. Ветки

| Ветка | Назначение |
|---|---|
| `main` | защищённая основная ветка; только через PR, всегда работоспособна и помечена тегом релиза |
| `feature/<кратко>` | новая функциональность (`feature/hotel-booking`) |
| `fix/<кратко>` | исправление дефекта (`fix/fee-refund-rule`) |
| `docs/<кратко>` | документация (`docs/api-description`) |
| `chore/<кратко>` | обслуживание (`chore/bump-ruff`) |

Ветка создаётся от актуального `main`, живёт недолго и удаляется после слияния.

## 4. Коммиты

Формат сообщения — Conventional Commits на русском языке:

```
<тип>(<область>): <краткое описание в повелительном наклонении>

<необязательное пояснение: что и почему>
```

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`.

Примеры осмысленной истории коммитов одной функции:

```
feat(hotel): добавить сущность брони гостиницы
feat(hotel): реализовать правило срока подтверждения брони
test(hotel): покрыть тестами подтверждение и истечение брони
docs(hotel): описать методы API для гостиницы
```

Запрещено: сообщения вида `fix`, `update`, `правки`, `WIP`, один гигантский коммит на всю
функцию.

## 5. Запрос на слияние (Pull Request)

> Запрос на слияние создаётся **только через веб-интерфейс GitHub** — команды `git` для этого
> не существует. После `git push -u origin <ветка>` откройте
> `https://github.com/Galaxy-1337/PopiKazaryan_DevOps_2026/pulls` → **New pull request**,
> укажите `main` как base и свою ветку как compare.

Шаблон описания PR:

```markdown
## Задача
Closes #12 — учёт потребности в гостинице

## Что сделано
- добавлены модель, схема и API брони гостиницы
- реализовано правило срока подтверждения (48 часов)
- добавлены тесты на подтверждение, истечение и отмену брони

## Как проверить
1. make verify
2. make run, открыть /ui → вкладка «Гостиница»
3. создать бронь по принятой заявке и подтвердить её

## Чек-лист
- [x] make verify проходит локально
- [x] добавлены или обновлены тесты
- [x] обновлена документация (README / docs/API.md / docs/DATA_MODEL.md)
- [x] секреты и локальные файлы не попали в коммит
```

Требования к PR:

1. Заголовок описывает результат, а не процесс.
2. Указана связанная задача (`Closes #N`).
3. Изменения критических файлов приёмки перечислены отдельным пунктом и проверяются
   ревьюером отдельно (см. п. 6).
4. CI по PR должен быть зелёным. Красный CI — блокирующее замечание.
5. Слияние выполняет автор после получения одобрения; используется squash или merge commit
   с осмысленным сообщением.

## 6. Изменения критических файлов приёмки

Особый контроль требуется для файлов, которые определяют, что считается «правильным»:

| Файл | Почему критичен |
|---|---|
| `.github/workflows/ci.yml` | задаёт состав автоматических проверок |
| `Makefile`, `scripts/dev.ps1` | определяет обязательные локальные команды |
| `scripts/smoke.py`, `scripts/container_check.py` | проверка работоспособности |
| `tests/conftest.py` | общая настройка тестов |
| `pyproject.toml` | правила анализа, пороги, исключения |
| `Dockerfile`, `docker-compose.yml` | среда эксплуатации |

Правила: такие изменения обязаны быть выделены в описании PR, не могут «попутно» ослаблять
проверки и должны быть явно одобрены ревьюером (второй участник команды или преподаватель).

## 7. Запрещённые действия

- Пушить напрямую в `main` и вливать PR без пройденного CI.
- Коммитить секреты: `.env`, пароли, токены, ключи, строки подключения с паролем.
- Коммитить локальные и сгенерированные файлы: `data/`, `backups/`, `.venv/`, `__pycache__/`,
  `*.db`, логи. Эти шаблоны уже перечислены в `.gitignore`.
- Удалять или отключать тесты, снижать пороги качества, добавлять `# noqa` без причины,
  исключать каталоги из анализа, ослаблять или отключать шаги CI ради прохождения проверки.
- Изменять проверочные файлы в том же коммите, что и проверяемый код, без отдельного
  обоснования в PR.
- Форс-пушить в `main`, переписывать историю общей ветки, удалять теги релизов.
- Коммитить код, который не проходит `make verify`.
- Оставлять в коде закомментированные блоки и отладочные выводы.

## 8. Порядок приёмки

### 8.1 Автоматическая приёмка (CI)

При каждом push и при каждом PR GitHub Actions (`.github/workflows/ci.yml`) выполняет две
группы проверок:

1. **Локальные проверки и тесты** — форматирование, статический анализ, pytest, дымовая
   проверка приложения, применение схемы БД.
2. **Сборка и проверка контейнера** — сборка образа, запуск контейнера, проверка `/health`
   внутри контейнера.

Изменение не принимается, пока обе группы не зелёные.

### 8.2 Организационная приёмка (review)

Ревьюер проверяет:

- соответствие изменения поставленной задаче и правилам предметной области;
- наличие и качество тестов на новое поведение;
- отсутствие секретов и локальных файлов в коммите;
- актуальность документации (`README.md`, `docs/API.md`, `docs/DATA_MODEL.md`);
- читаемость кода и осмысленность истории коммитов.

### 8.3 Финальная приёмка (защита)

Финальная приёмка всегда включает **живую демонстрацию** и **контрольное изменение**:

1. Показать путь изменения: задача → ветка → коммиты → PR → CI → merge → тег версии.
2. Объяснить правила внесения изменений (разделы 2, 7, 8).
3. Внести небольшое изменение «здесь и сейчас», провести его через ветку и PR, показать
   зелёный CI и слияние.
4. Показать, что секреты и локальные файлы не попадают в репозиторий
   (`git status --ignored`, `git check-ignore -v .env`).

Порядок подготовки и точные команды — в [`docs/DEFENSE_GUIDE.md`](docs/DEFENSE_GUIDE.md).

## 9. Релизы

1. Версия приложения хранится в `app/__init__.py` (`__version__`) и в `pyproject.toml`.
2. Релиз оформляется тегом на `main` после слияния PR: `git tag -a v0.1.0 -m "..."`.
3. Тег отправляется в репозиторий: `git push origin v0.1.0`.
4. В `README.md` в таблице «Версии» появляется запись об изменениях релиза.
5. Исправления после релиза выпускаются следующей версией (`v0.1.1`), а не перезаписью тега.

## 10. Ежедневный цикл работы (шпаргалка)

```bash
# 1. Начать работу
git switch main
git pull --ff-only
git switch -c feature/hotel-booking

# 2. Работать и проверять
make verify

# 3. Зафиксировать изменения
git add .
git commit -m "feat(hotel): добавить сущность брони гостиницы"

# 4. Отправить и создать PR
git push -u origin feature/hotel-booking

# 5. После слияния PR — обновить main и удалить ветку
git switch main
git pull --ff-only
git branch -d feature/hotel-booking
```
