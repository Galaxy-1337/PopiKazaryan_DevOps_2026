# Подготовка к защите лабораторной работы №1

Практическое руководство: что установить, что запустить, какие команды выполнить и что
показать. Рассчитано на защиту «здесь и сейчас», включая контрольное изменение.

---

## 1. Что нужно установить на свой компьютер

| Программа | Зачем | Проверка |
|---|---|---|
| **Python 3.11+** | запуск приложения и тестов | `python --version` |
| **Git** | работа с репозиторием | `git --version` |
| **Visual Studio Code** | основная среда разработки | `code --version` |
| **Расширения VS Code**: Python, Ruff, GitLens, Docker, GitHub Pull Requests | подсветка, форматирование, история, PR | панель Extensions |
| **Docker Desktop** *(не обязательно, но желательно)* | показ контейнерного окружения | `docker --version` |
| **GNU make** *(не обязательно)* | команды вида `make verify` | `make --version` |
| **Браузер** (Chrome/Edge) | веб-интерфейс и Swagger UI | — |

Если `make` не установлен, используйте полный аналог: `.\scripts\dev.ps1 <команда>`.
Установить make можно так: `winget install ezwinports.make`, затем перезапустить терминал.


## 4. Сценарий защиты: четыре обязательных показа

Лабораторная работа проверяет четыре пункта. Ниже — что именно делать и говорить.

### Показ 1. «Путь изменения от задачи до тега версии»

**Где:** терминал + браузер с GitHub.

```powershell
git log --oneline --graph --decorate --all -25
git tag -n
git show v0.1.0 --stat
```

**Что говорить:**

> Вот задача №4 в Issues — учёт потребности в гостинице. Под неё создана ветка
> `feature/4-hotel-booking`. В ветке четыре осмысленных коммита: сущность, правило срока
> подтверждения, тесты, документация. Из ветки создан Pull Request; CI прошёл две группы
> проверок — локальные проверки с тестами и сборку контейнера с проверкой `/health`. После
> одобрения PR слит в `main`, ветка удалена. Релиз отмечен аннотированным тегом `v0.1.0`.

Показать на GitHub: **Issues** (задача) → **Pull requests → Closed** (PR с зелёными
check-ами) → **Code → commits** (коммиты) → **Tags / Releases** (тег `v0.1.0`).

> **Важно про PR.** Запрос на слияние создаётся только через веб-интерфейс GitHub: команды
> `git` для этого нет. Ветки уже отправлены в репозиторий, поэтому достаточно открыть
> `https://github.com/Galaxy-1337/PopiKazaryan_DevOps_2026/pulls` → **New pull request**,
> выбрать `main` как base и нужную ветку как compare, заполнить описание и нажать
> **Create pull request**. Слияние выполняется кнопкой **Merge pull request**. Если
> преподаватель просит показать именно процесс в реальном времени — сделайте это на шаге
> «Показ 3», ветка там создаётся заново.
>
> Готовые ветки в удалённом репозитории для демонстрации PR:
>
> | Ветка | Что содержит |
> |---|---|
> | `feature/1-mailing-list` | отчёт «список рассылки по организациям»: три коммита |
> | `chore/2-capacity-a`, `chore/3-capacity-b` | две ветки, изменившие одну строку `.env.example` — источник конфликта слияния |

### Показ 2. «Объяснить правила внесения изменений»

**Где:** файлы [`CONTRIBUTING.md`](../CONTRIBUTING.md) и [`docs/GIT_WORKFLOW.md`](GIT_WORKFLOW.md).

**Что говорить (коротко, четыре тезиса):**

1. Любое изменение начинается с задачи и делается в отдельной ветке; прямой push в `main`
   запрещён — только через Pull Request.
2. Перед коммитом обязательно выполняется `make verify`: форматирование, статический анализ,
   55 тестов, дымовая проверка приложения. Пока не зелёно — коммитить нельзя.
3. Запрещено коммитить секреты и локальные файлы (`.env`, `data/`, `backups/`, `*.db`),
   удалять тесты, отключать анализаторы и ослаблять CI.
4. Изменения критических файлов приёмки (CI, Makefile, скрипты проверок, `pyproject.toml`,
   Docker) выделяются в PR отдельно и проверяются ревьюером особо.
5. Приёмка: автоматическая (CI), организационная (review) и финальная (живая демонстрация
   плюс контрольное изменение).

**Команда, подтверждающая правило:**

```powershell
git log --oneline main -1          # прямой коммит в main только через PR
git check-ignore -v .env data/ backups/
```

### Показ 3. «Внести небольшое изменение и провести его через ветку и PR»

Готовый сценарий на 4 минуты. Изменение — текст приветствия на странице интерфейса.

```powershell
# 1. Создать задачу в GitHub: Issues → New issue
#    Заголовок: «Уточнить подзаголовок на главной странице»   (например, это задача #15)

# 2. Ветка от актуального main
git switch main
git pull --ff-only
git switch -c feature/15-ui-subtitle
```

3. В VS Code открыть `app/templates/index.html` и изменить подзаголовок в шапке:

```html
<!-- было -->
<small>учёт участников, заявок, оргвзносов, тезисов и гостиницы</small>
<!-- стало -->
<small>учёт участников, заявок, оргвзносов, тезисов и потребности в гостинице</small>
```

4. Проверить локально:

```powershell
.\scripts\dev.ps1 verify
```

5. Закоммитить и отправить:

```powershell
git add app/templates/index.html
git commit -m "feat(ui): уточнить подзаголовок на главной странице (#15)"
git push -u origin feature/15-ui-subtitle
```

6. На GitHub: **Compare & pull request** → заполнить описание (указать `Closes #15`) →
   дождаться зелёного CI → **Merge pull request** → **Delete branch**.

7. Вернуться к main:

```powershell
git switch main
git pull --ff-only
git branch -d feature/15-ui-subtitle
git log --oneline -3
```

**Что говорить:**

> Изменение небольшое, но проходит полный цикл: задача, ветка, локальная проверка `verify`,
> осмысленный коммит, push, Pull Request, зелёный CI, слияние в main и удаление ветки. Точно
> так же проходит любое изменение, включая крупные функции.

> Если нужно показать изменение в интерфейсе — после слияния перезапустить сервер
> (`Ctrl+C`, затем `.\scripts\dev.ps1 run`) и обновить страницу в браузере.

### Показ 4. «Секреты и локальные файлы не попадают в репозиторий»

```powershell
# Файл .env существует локально, но игнорируется
Test-Path .env
git check-ignore -v .env

# Список игнорируемых файлов
git status --ignored --short

# Что реально отслеживается: в списке нет .env, *.db, backups/
git ls-files | Select-String -Pattern "\.env|\.db|backups" 
# (вывод должен содержать только .env.example — это безопасный шаблон)

# История по .env: коммитов нет
git log --all --oneline -- .env

# Секреты читаются только из окружения
Get-Content .env.example | Select-Object -First 20
```

**Что говорить:**

> Все секреты — только в переменных окружения. В репозитории лежит `.env.example` с
> безопасными значениями-заглушками, а рабочий `.env` добавлен в `.gitignore`. Каталоги
> `data/`, `backups/`, `*.db`, `.venv/`, `__pycache__/` тоже игнорируются, поэтому база данных
> и резервные копии в репозиторий не попадают. Проверить можно командами `git check-ignore`
> и `git ls-files`.

> Важно: если реальный пароль всё же попал в историю — его нужно сменить, потому что удаление
> файла коммитом не убирает содержимое из истории.

## 5. Живая демонстрация приложения (2–3 минуты)

Показывайте по одному сценарию на каждую сущность. Данные уже есть — их создаёт
`app/seed.py`.

### Вкладка «Сводка»

Показать: число заявок и участников, суммы оргвзносов, количество тезисов, броней и гостей,
распределение по статусам.

> Отчёт собирается одним запросом к API: `GET /api/v1/reports/conference/1`. Он нужен
> оргкомитету, чтобы планировать рассылку и размещение.

### Вкладка «Заявки»

1. Нажать **Новая заявка**, выбрать секцию и участника, ввести тему → **Создать черновик**.
   Появится заявка со статусом `черновик`.
2. Нажать **Подать** у этой заявки → статус станет `подана`.
3. Нажать **Принять** → статус `принята`.
4. Вернуться во вкладку **Оргвзносы** → появилось начисление на 3 500 ₽ `начислен`.
5. Вернуться во вкладку **Приглашения** → появилось приглашение `в очереди`.

> При принятии заявки сработали два правила: автоматически начислен оргвзнос в размере
> взноса конференции и приглашение поставлено в очередь рассылки. Это правила предметной
> области, они реализованы в `app/services.py` и покрыты тестами.

### Проверка правила «нет свободных мест»

Вместимость секции — 3. Подайте четвёртую заявку в ту же секцию и нажмите **Подать** —
всплывёт ошибка.

> Секция заполнена: правило `section_capacity_exceeded`. Обратите внимание на единый формат
> ошибки — код, понятное сообщение и HTTP-статус 409.

### Вкладка «Оргвзносы»

Нажать **Оплатить** → статус `оплачен`. Нажать **Оплатить** повторно — ошибка
`fee_already_paid`. Отозвать заявку и нажать **Вернуть** → статус `возвращён`.

> Возврат возможен только по оплаченному взносу и только по отозванной или отклонённой
> заявке. Это правило предметной области, а не просто смена статуса.

### Вкладка «Приглашения»

Нажать **Отправить** → статус `отправлено`. Во второй строке нажать **Смоделировать ошибку**
→ статус `ошибка`, число попыток увеличилось.

> Очередь рассылки допускает повторную отправку после ошибки: хранится число попыток и текст
> последней ошибки, поэтому сбой не теряется.

### Вкладка «Гостиница»

Нажать **Гостиница** у принятой заявки → бронь создана со статусом `запрошена` и сроком
подтверждения. Нажать **Подтвердить** → статус `подтверждена`.

> У брони есть срок подтверждения (48 часов). Просроченная бронь не может быть подтверждена и
> помечается как истёкшая — правило `hotel_confirmation_expired`. Дистанционному участнику
> гостиница недоступна, а даты проживания должны укладываться в даты конференции.

### Вкладка «Тезисы»

Нажать **Принять (8)** → статус `приняты`. Если нажать **Отклонить (4)** — статус `отклонены`.

> Порог принятия тезисов — 6 баллов из 10. Оценка вне диапазона 1–10 отклоняется валидацией
> с ответом 422.

### Swagger UI — показать API

Открыть <http://127.0.0.1:8000/docs>, развернуть `GET /api/v1/reports/conference/{conference_id}`,
нажать **Try it out**, ввести `1`, **Execute** — показать ответ JSON.

> Документация OpenAPI формируется автоматически из кода, поэтому она всегда соответствует
> реализации. Это же описание можно использовать для проверки методов в Postman.

## 8. Вероятные вопросы и короткие ответы

| Вопрос | Ответ |
|---|---|
| Почему FastAPI? | автоматическая документация OpenAPI (`/docs`), строгая валидация через Pydantic, минимальный код для HTTP API |
| Где бизнес-логика? | в `app/services.py` — правила переходов статусов, взносы, тезисы, гостиница; роутеры только принимают запрос и вызывают сервис |
| Почему правила не только в БД? | часть правил зависит от состояния нескольких записей и от времени (заполненность секции, срок подтверждения брони) — это проверяется на уровне сервиса, а базовые инварианты продублированы ограничениями СУБД |
| Что такое `X-Request-ID`? | сквозной идентификатор запроса; по нему ищут запись в журнале при разборе инцидента |
| Как проверяется работоспособность? | `GET /health` выполняет `SELECT 1` к базе; используется в `HEALTHCHECK` контейнера, в CI и в `make verify` |
| Чем отличается локальный запуск от контейнерного? | локально SQLite и `APP_DEBUG=true`; в контейнерах PostgreSQL 16, `APP_DEBUG=false`, тома для данных, проверка `pg_isready` перед стартом приложения |
| Как хранятся секреты? | только в переменных окружения; в репозитории `.env.example` с заглушками, рабочий `.env` в `.gitignore` |
| Что будет при отзыве заявки? | активная бронь гостиницы отменяется, неоплаченный оргвзнос отменяется, место в секции освобождается |
| Что мешает оплатить взнос дважды? | правило в сервисе (`fee_already_paid`) и статусная модель взноса |
| Как вы убеждаетесь, что изменение ничего не сломало? | `make verify`: форматирование, статический анализ, 55 тестов, дымовая проверка; плюс CI на каждый push и PR |
| Почему запрещено править CI ради зелёного статуса? | это ослабление контроля: проверка перестаёт ловить дефекты, а изменение становится непроверенным |
| Как моделировали конфликт слияния? | две ветки (`chore/2-capacity-a` и `chore/3-capacity-b`) меняли одну строку `SECTION_CAPACITY` в `.env.example`; вторая ветка дала конфликт, он разрешён вручную с сохранением нужного значения, затем `make verify` и коммит слияния |
| Что делать, если в репозиторий попал пароль? | удалить файл из индекса (`git rm --cached`), закоммитить и **сменить** сам пароль, так как он считается скомпрометированным |

## 9. Если что-то пошло не так

| Симптом | Причина и решение |
|---|---|
| `python: command not found` | Python не в PATH — переустановить с галочкой «Add Python to PATH» |
| `ModuleNotFoundError: fastapi` | не выполнена настройка — `.\scripts\dev.ps1 setup` |
| Порт 8000 занят | `.\scripts\dev.ps1 run` на другом порту: `.\scripts\dev.ps1 run -Port 8010` |
| `database is locked` | остановить второй запущенный экземпляр приложения |
| Интерфейс пустой, ошибки в консоли | открыть `/docs`, проверить `/health`; перезапустить сервер и обновить страницу с `Ctrl+F5` |
| Исчезли демонстрационные данные | удалить `data/conference.db`, затем `migrate` и `run` — данные создадутся заново |
| `ruff check` ругается на формат | `.\scripts\dev.ps1 format` и повторить `verify` |
| CI красный на GitHub | открыть вкладку **Actions** → падающий шаг → исправить локально, затем новый коммит в ту же ветку |
| `git push` просит пароль | использовать Personal Access Token вместо пароля или настроить Git Credential Manager |
| Конфликт при `git pull` | разрешить по инструкции [`docs/GIT_WORKFLOW.md`](GIT_WORKFLOW.md), шаг 7 |

## 10. Чек-лист перед входом в аудиторию

- [ ] `git switch main && git pull --ff-only` — репозиторий актуален.
- [ ] `.\scripts\dev.ps1 verify` — `55 passed`, проверки зелёные.
- [ ] База в чистом демонстрационном состоянии (при необходимости пересоздана).
- [ ] Сервер запущен, открыты вкладки `/` и `/docs`.
- [ ] GitHub открыт: Issues, Pull requests, Actions, Tags.
- [ ] VS Code открыт на папке проекта, интерпретатор `.venv` выбран.
- [ ] Открыты `CONTRIBUTING.md`, `docs/GIT_WORKFLOW.md`, `docs/DATA_MODEL.md`.
- [ ] Проверено `git check-ignore -v .env` — секреты игнорируются.
- [ ] Готов текст задачи для контрольного изменения (заранее созданная issue).
- [ ] Знаете наизусть: `verify`, `run`, `switch -c`, `add`, `commit`, `push`, `tag`.
