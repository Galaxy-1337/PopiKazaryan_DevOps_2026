## Назначение системы

Приложение автоматизирует работу оргкомитета конференции:

| Область | Что автоматизируется |
|---|---|
| Участники | единый реестр участников с контактами, организацией и ролью |
| Заявки | приём и обработка заявок на участие в секциях, решения программного комитета |
| Тезисы | приём тезисов докладов и их рецензирование с порогом принятия |
| Оргвзносы | начисление, оплата и возврат взносов по заявкам |
| Приглашения | очередь рассылки приглашений и контроль ошибок отправки |
| Гостиница | учёт потребности в проживании, сроков подтверждения и числа гостей |
| Отчётность | сводные отчёты по конференции для планирования и рассылок |

Задача системы — свести в одно место весь путь участника: от подачи заявки до заселения в
гостиницу, — и дать оргкомитету отчёт, по которому можно планировать рассылку и размещение.

## Категории пользователей

| Роль | Возможности |
|---|---|
| **Организатор (администратор)** | создаёт конференции и секции, управляет участниками, принимает решения по заявкам, контролирует взносы, рассылает приглашения, подтверждает брони гостиницы, получает отчёты |
| **Участник (слушатель)** | подаёт заявку на участие, указывает потребность в гостинице, оплачивает оргвзнос |
| **Докладчик** | делает всё то же, что участник, и дополнительно подаёт тезисы доклада |
| **Рецензент** | получает тезисы на рецензию и выставляет оценку с комментарием |

## Основные сценарии

1. **Подготовка конференции.** Организатор создаёт конференцию (название, даты, место,
   размер оргвзноса) и открывает тематические секции с ограниченной вместимостью.
2. **Подача заявки.** Участник создаёт заявку (тема, аннотация, формат участия, потребность
   в гостинице), затем подаёт её на рассмотрение.
3. **Рассмотрение заявки.** Организатор принимает или отклоняет заявку. При принятии система
   автоматически начисляет оргвзнос и ставит приглашение в очередь рассылки.
4. **Оплата оргвзноса.** Организатор регистрирует оплату взноса; при отказе от участия
   оформляет возврат.
5. **Работа с тезисами.** Докладчик добавляет тезисы по принятой заявке; рецензент выставляет
   оценку, по которой система принимает решение о публикации.
6. **Гостиница.** Организатор оформляет бронь на участника; бронь нужно подтвердить в
   установленный срок, иначе она помечается как истёкшая.
7. **Рассылка и отчёты.** Организатор выгружает очередь неотправленных приглашений и
   формирует сводный отчёт по конференции.

## Обязательные правила работы

Правила реализованы в `app/services.py` и проверяются автоматическими тестами.

| № | Правило | Код ошибки |
|---|---|---|
| 1 | Жизненный цикл заявки: `черновик → подана → принята` / `отклонена`; отзыв из `черновика`, `подана`, `принята` | `invalid_status_transition` |
| 2 | Приём заявок только по активной конференции | `conference_inactive` |
| 3 | Приём заявки только в открытую секцию | `section_closed` |
| 4 | Число заявок в секции не может превышать её вместимость; место освобождается при отклонении или отзыве | `section_capacity_exceeded` |
| 5 | Один участник — одна заявка в секции данной конференции | `application_duplicate` |
| 6 | При принятии заявки автоматически начисляется оргвзнос и создаётся приглашение в очереди рассылки | — |
| 7 | Оргвзнос нельзя оплатить дважды и нельзя оплатить отменённый/возвращённый | `fee_already_paid`, `fee_not_payable` |
| 8 | Возврат только по оплаченному взносу и только по отозванной/отклонённой заявке | `fee_not_paid`, `refund_not_allowed_for_status` |
| 9 | Тезисы принимаются только по принятой заявке и в пределах допустимого размера файла | `thesis_requires_accepted_application`, `thesis_file_too_large` |
| 10 | Тезисы принимаются при оценке рецензента не ниже 6 из 10 | — |
| 11 | Гостиница недоступна для дистанционного формата участия | `hotel_not_allowed_for_online` |
| 12 | Даты проживания должны укладываться в даты конференции | `hotel_dates_out_of_conference` |
| 13 | Одна активная бронь на заявку | `hotel_booking_exists` |
| 14 | Бронь, не подтверждённая в срок (по умолчанию 48 часов), не может быть подтверждена | `hotel_confirmation_expired` |
| 15 | При отзыве заявки активная бронь отменяется, неоплаченный взнос отменяется | — |

## Быстрый старт

Проект можно запускать тремя способами. Команды одинаковы во всех вариантах: `make` — основной
интерфейс, `scripts/dev.ps1` — его полный аналог для Windows без GNU make, `docker compose` —
прямое управление контейнерами.

### Способ 1. Локально через GNU make (SQLite)

```bash
make setup      # один раз: виртуальное окружение, зависимости, .env
make migrate    # создание схемы базы данных
make run        # запуск на http://127.0.0.1:8000
```

Установка GNU make в Windows (один раз):

```powershell
winget install ezwinports.make
# затем перезапустить терминал и проверить: make --version
```

### Способ 2. Локально через скрипт PowerShell (SQLite)

Тот же набор команд без установки make — результат идентичен:

```powershell
.\scripts\dev.ps1 setup      # venv, зависимости, .env
.\scripts\dev.ps1 migrate    # создание схемы БД
.\scripts\dev.ps1 run        # запуск на http://127.0.0.1:8000
```

### Способ 3. В контейнерах (приложение + PostgreSQL)

```bash
make up              # сборка и запуск app + db
make container-check # проверка /health
make logs            # журналы
make down            # остановка
```

То же самое напрямую, без make:

```powershell
docker compose up --build -d
docker compose ps
docker compose down
```

Во всех случаях откройте <http://127.0.0.1:8000> — это веб-интерфейс,
<http://127.0.0.1:8000/docs> — Swagger UI, <http://127.0.0.1:8000/health> — проверка
работоспособности.

| Что сравниваем | Способ 1 и 2 (локально) | Способ 3 (контейнеры) |
|---|---|---|
| СУБД | SQLite, файл `data/conference.db` | PostgreSQL 16, том `conference_db-data` |
| Поле `app_env` в `/health` | `local` | `docker` |
| Порт | 8000 | 8000 |
| Требуется Docker | нет | да |

Локальный и контейнерный запуски занимают **один и тот же порт 8000**, поэтому одновременно
они работать не могут: перед переключением остановите один (`Ctrl+C` или `make down`).

## Единый командный интерфейс

Все обязательные операции выполняются одной командой. Основной интерфейс — `make`; в Windows без
GNU make используется `scripts/dev.ps1` с теми же именами команд.

Makefile не использует Unix-утилиты (`grep`, `awk`, `sed`, `rm`, `find`, `cp`), поэтому одинаково
работает и в Windows, и в Linux: разбор Makefile, создание `.env` и очистка каталогов выполнены
небольшими скриптами на Python (`scripts/make_help.py`, `scripts/make_setup_env.py`,
`scripts/make_clean.py`).

| Команда | Назначение |
|---|---|
| `make setup` | первоначальная настройка: venv, зависимости, `.env` |
| `make run` | локальный запуск приложения |
| `make test` | автоматические тесты (pytest) |
| `make quality` | форматирование и статический анализ |
| `make lint` | только статический анализ (ruff check) |
| `make format` | автоматическое форматирование кода |
| `make migrate` | применение миграций / создание схемы БД |
| `make backup` | создание резервной копии БД |
| `make restore FILE=...` | восстановление БД из копии |
| `make verify` | **полный набор локальных проверок перед коммитом** |
| `make up` / `make down` | запуск и остановка контейнерного окружения |
| `make logs` / `make shell` | логи контейнеров / оболочка внутри контейнера |
| `make container-check` | проверка контейнера через `/health` |
| `make version` | версия приложения |
| `make clean` | удаление кэшей и виртуального окружения |

`make verify` — это обязательная проверка перед каждым запросом на слияние. Она выполняет
`ruff format --check`, `ruff check`, `pytest` и дымовую проверку приложения (`scripts/smoke.py`).

## Конфигурация

Все параметры задаются переменными окружения; шаблон — `.env.example` (копируется в `.env`,
который **не** попадает в репозиторий).

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_NAME` | `Конференция` | название приложения |
| `APP_ENV` | `local` | окружение: `local`, `docker`, `ci` |
| `APP_DEBUG` | `true` | подробные сообщения об ошибках (в эксплуатации — `false`) |
| `APP_HOST` / `APP_PORT` | `127.0.0.1` / `8000` | адрес и порт приложения |
| `DATABASE_URL` | `sqlite+pysqlite:///./data/conference.db` | строка подключения к БД |
| `ADMIN_EMAIL` | `admin@conference.local` | e-mail администратора (создаётся при старте) |
| `ADMIN_PASSWORD` | `ChangeMe_12345` | пароль администратора (**сменить!**) |
| `ADMIN_FULL_NAME` | `Администратор программы` | ФИО администратора |
| `SEED_DEMO_DATA` | `true` | создавать демонстрационные данные |
| `SECTION_CAPACITY` | `3` | вместимость секции по умолчанию |
| `HOTEL_CONFIRMATION_HOURS` | `48` | срок подтверждения брони, часы |
| `ABSTRACT_MAX_SIZE_KB` | `512` | предел размера файла тезисов, КБ |

Пример строки подключения к PostgreSQL:

```
DATABASE_URL=postgresql+psycopg2://conference:conference@127.0.0.1:5432/conference
```

## HTTP API

Полное описание — [`docs/API.md`](docs/API.md) и живая схема OpenAPI на `/docs`, `/redoc`,
`/openapi.json`.

Краткий состав:

- `GET /health`, `GET /version` — служебные адреса;
- `GET|POST /api/v1/conferences`, `GET|PATCH|DELETE /api/v1/conferences/{id}`;
- `GET|POST /api/v1/sections`, `GET|PATCH|DELETE /api/v1/sections/{id}`;
- `GET|POST /api/v1/participants`, `GET|PATCH|DELETE /api/v1/participants/{id}`;
- `GET|POST /api/v1/applications`, `PATCH|DELETE /api/v1/applications/{id}`,
  `POST /api/v1/applications/{id}/submit|decision|withdraw`;
- `GET|POST /api/v1/invitations`, `POST /api/v1/invitations/{id}/send`;
- `GET|POST /api/v1/fees`, `POST /api/v1/fees/{id}/pay|refund`;
- `GET /api/v1/theses`, `POST /api/v1/applications/{id}/theses`, `POST /api/v1/theses/{id}/review`;
- `GET|POST /api/v1/hotel-bookings`, `POST /api/v1/hotel-bookings/{id}/confirm`,
  `POST /api/v1/hotel-bookings/expire-stale`;
- `GET /api/v1/reports/conference/{id}`, `GET /api/v1/reports/invitations-queue`,
  `GET /api/v1/reports/mailing-list/{id}`.

Единый формат ошибки:

```json
{
  "error": {
    "code": "section_capacity_exceeded",
    "message": "В секции «CI/CD и автоматизация релизов» нет свободных мест (3 из 3 занято)",
    "details": null
  }
}
```

## Веб-интерфейс

Одна страница с вкладками, которые обращаются к собственному API:

| Вкладка | Что показывает | Действия |
|---|---|---|
| Сводка | ключевые показатели и распределение по статусам | обновление отчёта |
| Заявки | список заявок с фильтром по статусу | создать черновик, подать, принять, отклонить, отозвать, добавить тезисы, оформить гостиницу |
| Оргвзносы | начисления по заявкам | оплатить, вернуть |
| Приглашения | очередь рассылки | отправить, смоделировать ошибку отправки |
| Гостиница | брони и сроки подтверждения | подтвердить бронь |
| Тезисы | тезисы и результаты рецензии | принять или отклонить рецензией |

Интерфейс намеренно использует обычные `fetch`-запросы к API: то же самое можно сделать через
Swagger UI, curl или Postman — поведение и правила одинаковы.

## Проверка работоспособности

```bash
curl http://127.0.0.1:8000/health
```

```json
{
  "status": "ok",
  "version": "0.1.0",
  "database": "ok",
  "app_env": "local",
  "checked_at": "2026-01-15T10:00:00Z"
}
```

Если база данных недоступна, поле `database` содержит описание ошибки, а `status` принимает
значение `degraded`. Этот адрес используется контейнерным `HEALTHCHECK`, скриптом
`scripts/container_check.py` и шагом проверки в CI.

## Тесты и качество кода

```bash
make verify     # полный набор: форматирование, анализ, тесты, дымовая проверка
make test       # только тесты
make quality    # только форматирование и анализ
```

- **58 автоматических тестов** (pytest) покрывают служебные адреса, конференции и секции,
  участников, заявки, оргвзносы, приглашения, тезисы, гостиницу и отчёты.
- Отдельные тесты проверяют **каждое обязательное правило** предметной области и
  **некорректные запросы** (422, 404, 409, единый формат ошибки).
- **ruff** обеспечивает единый стиль (`ruff format`) и статический анализ (`ruff check`).

Что запрещено: удалять тесты, отключать анализаторы, снижать пороги качества и ослаблять CI
ради прохождения проверки. Изменения критических файлов приёмки (`.github/workflows/ci.yml`,
`Makefile`, `scripts/`, `tests/conftest.py`, `pyproject.toml`) должны быть видны в запросе на
слияние и проверяются отдельно.

## Контейнерное окружение

```bash
make up              # сборка и запуск app + db
make container-check # проверка /health из контейнера
make logs            # логи
make down            # остановка
docker compose down -v   # остановка с удалением тома базы данных
```

Состав: сервис `app` (образ на основе `python:3.12-slim`, запуск от непривилегированного
пользователя, `HEALTHCHECK` через `/health`) и сервис `db` (`postgres:16-alpine` с томом
`db-data` и проверкой `pg_isready`). Приложение стартует только после готовности базы.

### Если Docker Desktop не запускается

Типовая причина на Windows — не установлен WSL 2, который Docker Desktop использует как
виртуальную машину. Для включения подготовлен скрипт `scripts/enable-wsl2.ps1`; его нужно
запустить **от имени администратора** и перезагрузить компьютер:

```powershell
# правый клик по PowerShell → «Запуск от имени администратора»
Set-Location "C:\Users\Иван\Desktop\ПЕРВЫЙ проект\DevOps"
.\scripts\enable-wsl2.ps1
```

Скрипт включает компоненты «Windows Subsystem for Linux» и «Платформа виртуальных машин»,
обновляет пакет WSL и печатает итоговое состояние; журнал сохраняется рядом со скриптом.
Приложение при этом работает и без Docker: локальный запуск использует SQLite.

## Резервное копирование

```bash
make backup                       # создать копию в backups/
make restore FILE=backups/...     # восстановить
python -m scripts.restore --list  # список копий
```

Для SQLite копируется файл базы, для PostgreSQL выполняется `pg_dump`. Перед восстановлением
текущая база сохраняется с суффиксом `.before-restore`. Каталог `backups/` исключён из
репозитория.

## Правила внесения изменений

Подробно — [`CONTRIBUTING.md`](CONTRIBUTING.md) и [`docs/GIT_WORKFLOW.md`](docs/GIT_WORKFLOW.md).

Кратко:

1. Любое изменение начинается с **задачи** (issue) и выполняется в **отдельной ветке**
   от `main`.
2. Перед коммитом обязательно выполняется **`make verify`**.
3. Изменение попадает в `main` **только через запрос на слияние** (pull request) с пройденным CI.
4. Запрещено: коммитить секреты и файлы `.env`, пушить напрямую в `main`, коммитить в
   `main` в обход PR, удалять тесты и ослаблять CI, отключать анализаторы.
5. Каждый релиз отмечается **тегом версии** (`v0.1.0`, ...).
6. Учебное упражнение по разрешению конфликта слияния выполнено отдельно от кода
   приложения: ветки `feature/2-teams-section` и `feature/3-section-capacity` правили одно
   место в `app/services.py`, конфликт разрешён вручную, результат закреплён коммитом
   слияния. Пошаговое описание — в [`docs/GIT_WORKFLOW.md`](docs/GIT_WORKFLOW.md), шаг 7.
